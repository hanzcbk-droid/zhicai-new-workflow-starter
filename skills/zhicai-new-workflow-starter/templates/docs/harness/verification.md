# 验收标准 · Verification

## 这个项目怎么算"做好了"（建项目时和用户一起定的）
1. {标准 1}
2. {标准 2}
3. {标准 3}

## L1 · 格式检查（智能体自检）
- [ ] {按项目类型写：命名、格式、存放位置、禁止出现的东西}

## L2 · 内容检查（智能体自检）
- [ ] 对照上面的合格标准逐条检查，每条都写出结果
- [ ] 引用、链接、附件都存在，也能打开
- [ ] 当前任务的 verification 步骤全部真的执行过

启动检查只覆盖它实际执行的结构与格式项目；跳过的检查不是通过。换新对话或其他智能体接续须另行实测，并分别记录结果。

## 证据怎么记
每项检查都写进 feature_list.json 对应任务的 evidence：查了什么、怎么查的、结果是什么。
只写"没问题""看起来可以"不算证据。

## L3 · 用户审阅
L1、L2 全部通过 → 状态改成 awaiting_review → 把产出和证据拿给用户看。
用户说"行" → 改成 passing。
用户说"不行" → 原因写进 notes。没有其他 in_progress 任务时改回 in_progress；已有其他任务进行中时，先将被退回任务标为 blocked 并说明等待返工，保留现有任务进度。用户要求立即返工时，先把原进行中任务标为 blocked 并记好暂停与恢复信息，再将退回任务设为 in_progress。
用户一直没回复 → 保持 awaiting_review，下次开工时提醒用户去审。不会自动当成通过。

## 独立评审打分表（重要交付时用）
条件允许时，找一个"没参与干活的"来评：开一个新的子智能体或新对话，或者直接请用户评。干活的自己给自己打分不算独立评审。

| 维度 | 看什么 | 0～2 分 |
| --- | --- | --- |
| 正确性 | 做出来的东西是不是用户要的 | |
| 验证 | 检查是不是真的跑过、有证据 | |
| 范围 | 有没有乱动别的东西 | |
| 可靠性 | 换个情况会不会就坏了 | |
| 好维护 | 别人或下一轮能不能看懂、接着改 | |
| 交接 | 下一轮能不能直接开工 | |

结论三选一：通过 / 返工（写清改哪里）/ 卡住（写清缺什么）。
